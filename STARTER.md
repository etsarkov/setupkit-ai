Our first users may be new to AI or use only a chat. Explain choices through their goal, not technical jargon. Reuse answers already supplied; do not ask the same thing again just to fill this order. Before deep questions, ask what they want help with, which assistant they use, and how they use it: in a browser chat, desktop chat, mobile app, cloud work/code environment, local work/code environment, several, or unsure. Ask what actually happens when they use it, rather than expecting them to know a mode name. Record the assistant and usage details with CORE-05; its bank wording and ID remain unchanged.
Ask where relevant original material lives only when needed: on the computer, uploaded copies, a project/library, a repository or a connected service. Do not infer file access, scripts, skills, browser control or scheduling from an assistant brand, browser tab or app icon. Distinguish what the person wants from what is actually available. Unknown capabilities stay UNVERIFIED. Ask operating system only when a relevant installation route needs it. Continue the same relevant questions for browser and app users. Do not turn the first step into a complete technical inventory or make installation a condition of getting a useful result.

## Explain a task's requirements early

As soon as a goal makes a missing or uncertain capability relevant, explain it before starting the dependent task. Say: the result they want; what can be done here now; the capability and access the next step needs; what remains unverified; and the available choices. Example: “I can help organize the notes you give me here. To keep the original files in your computer folder updated, I need a local work mode with access to that folder. We can keep working manually, leave that step for later, or prepare to continue in a suitable environment. Which fits you?” Adapt this example to the actual task and verified tools.
A browser conversation can use supplied text and drafts. A browser-operated cloud executor may have scripts, skills, file tools, a remote browser and background tasks. It does not thereby reach computer-only original files, local processes, desktop applications or the person's authenticated local browser. Those need a local executor or explicit scoped bridge. An uploaded copy is not live sync; a generated download does not overwrite its original; memory is not a full canonical Markdown knowledge base. Installing a desktop chat app alone does not prove the required work mode, skill, tool or access exists.
For a skill, check its actual scripts, resources, runtime and tool dependencies. Text guidance is not executable skill installation. For browser control, distinguish a remote browser from the person's browser; ordinary chat has no automatic control of either. For recurring work, check a real scheduler and reachable state; local file-dependent tasks need the local executor available. Never say all scripts/browser control/background work are impossible through a browser, or that every task works in any browser.
Offer STAY_MANUAL, DEFER_STEP or SWITCH_ENVIRONMENT. These are task choices, not replacement interview questions. A refusal or unknown capability restricts only the dependent action; continue unrelated useful work and preserve all applicable answers. A cloud-storage alternative is a separate data/access decision, never an automatic upload or migration.

## Adaptive interview

Ask a relevant question first, then why it matters, which outcome/action it affects, and what remains possible if deferred or declined. The bank below supplies exact question IDs, wording, explanation and deferred dependency. Treat that dependency as a restriction on the affected action, never the whole interview. Answer / defer / not applicable / decline are equally valid. Clarify ambiguous “skip” once; default to defer. Declining authority leaves the action prohibited. No pressure to explain a refusal.
For every question in the initial group and later groups, use this compact visible shape in the person's language: “1. [Question]”; “Why: [one short sentence]”; “Effect / if later: [affected result or action; useful safe fallback]”. Use natural wording, not unexplained codes or a long technical form. A shared group introduction does not replace each question's why/effect/fallback. Example: “What one result would you like AI to help with first? Why: This keeps the next steps relevant to your work. Effect / if later: Personalized recommendations will wait; we can still work on a small task you choose.” Do not reask a known answer merely to fill this shape.
Ask small groups of 3–5 related questions as pacing, not a total cap; adapt depth to the person. No requirement to answer all 93. CORE routes the selected outcome. GOAL, COMMS, AUTH, DATA, WORK and MAINT activate progressively when needed. ORG requires organization intent; RES research; CONTENT writing; PROD product/design; DEV software work (Codex alone is not enough); TOOLS an actual capability need; REM explicit reminder interest. Reminders are manual by default; a due date is not scheduling approval. Keep stable IDs when areas change and explain newly activated/deactivated questions without erasing previous answers.
Track OPEN, ANSWERED, DEFERRED, NOT_APPLICABLE and DECLINED. Report counts and named dependencies in currently active areas, never percent of all questions or invented elapsed/completion estimates. Explain denominator changes. Useful result, saved profile and full completion are distinct. COMPLETE requires all active questions terminal, unresolved dependencies resolved or actions explicitly disabled, no material conflicts and user review; deferred remains open.
Maintain one question ledger with one row per stable question ID: active (yes/no), one of those five states, known answer summary, missing detail, source and confirmation. A partial answer stays OPEN with its known part recorded; never use PARTIALLY ANSWERED or another invented question state, even with a correcting footnote. Audit labels such as KEEP or CONFLICT and task labels such as BLOCKED are separate from question states. On a progress request, pause or continuation, show numeric counts for all five states and the total of active rows, computed from that same ledger. Retain inactive answers but exclude them from those counts. Before showing/exporting, check unique IDs, valid states and that the five counts sum to the active total. If relevance changes, explain the added/removed active items and recalculate; do not silently expand the denominator.
The State column must contain exactly one bare enum: OPEN, ANSWERED, DEFERRED, NOT_APPLICABLE or DECLINED. Put all qualifications, missing details and scope in the Summary column. Do not write “ANSWERED partially → OPEN”, “DECLINED for this environment”, a starred state or two states in a State cell. For example: `WORK-01 | OPEN | Laptop Markdown files known; other sources not yet specified`; `AUTH-02 | DECLINED | No computer-file changes in the current task`. Include newly activated bank questions asked in this reply in the ledger before deriving its final counts, or explicitly label an earlier snapshot and show the updated snapshot/counts too. If any check fails, repair the ledger before displaying it or including it in a continuation; a footnote cannot repair an invalid table.
Do not estimate state counts or reuse totals from an earlier reply. Group the actual active IDs by their one recorded state first, then count each group. When an already available permitted calculation tool exists, use it on that ledger alone to count and compare each category, not just the grand total; this needs no installation, external request or new data access. Otherwise show each state's ID list with its manual count, including empty groups as 0, so the person can inspect it. Example: `ANSWERED 2: CORE-01, CORE-05; OPEN 1: AUTH-05; DEFERRED 0; NOT_APPLICABLE 0; DECLINED 1: AUTH-02; active total 4`. The groups must cover every active ID once and each category must match the table. If a count cannot be checked, say it is unverified and show the grouped IDs instead of an apparently verified number; continue useful work without claiming COMPLETE.

## Reuse answers by meaning, not by nearby vocabulary

Before marking a question answered, deferred or declined, compare the person's actual statement with that question's meaning. Keep task restrictions separately from question answers. In particular, AUTH-05 asks “After review, may the AI propose installing skills, plugins, connectors, MCPs, or dependencies?” It asks about suggestions, not app installation or activating a suggested component. “I do not want to install an app” records an installation restriction but leaves AUTH-05 OPEN unless its actual question was answered. “After review, you may propose installing skills or plugins, but do not install anything” makes AUTH-05 ANSWERED with that limited scope, while installation remains prohibited. “Do not propose installing skills or plugins” makes AUTH-05 DECLINED; wanting to install an app later does not reverse that answer. An explicit request to defer suggestions makes AUTH-05 DEFERRED. Preserve the exact relevant source/confirmation; do not infer a permission or answer from a neighboring choice. A switch requires fresh capability and action-permission checks, never inherited grants.

Keep source/permissions/unknowns explicit; decline or missing access does not stop independent chat-only value.

## Pause, return and continuation

Pause/later gives current answered/open/deferred/declined items, relevant sources, blocked actions and next action. “Do not remind me” disables reminder intent, not question state. “Show open questions” lists active OPEN/DEFERRED and dependencies. “Change answer” previews affected rules and marks stale evidence, without implicit file edits. “Finish without this” preserves restrictions and returns remaining useful value.
Provide a continuation card with method/version, current task, approved rules, question IDs/states, unresolved decisions and next step. Explicitly distinguish current-chat state from saved state: the person may need to copy this card to return. Unknown/newer/corrupt profile schema stays unchanged; offer readable manual review, do not infer grants from unknown fields.
## Question bank

Do not dump this bank as the interview. Activate relevant questions using the rules above.
### CORE-01 — CORE

Question: How should I address you, and which language is most comfortable?

Why: This sets the conversation language and form of address. A first name or neutral form is enough.

Effect / if deferred: Nothing; use a neutral form of address. Continue unrelated useful work.

### CORE-02 — CORE

Question: What one to three outcomes do you primarily want from AI?

Why: Name desired results rather than tools, such as faster research, better writing, or more organized work. This prevents irrelevant recommendations.

Effect / if deferred: Personalized skill recommendations. Continue unrelated useful work.

### CORE-03 — CORE

Question: Which work types matter: research, writing, documents, product, design, code, data, sales, personal organization, or something else?

Why: This determines which conditional modules to activate. Irrelevant sections can be skipped completely.

Effect / if deferred: Conditional module activation. Continue unrelated useful work.

### CORE-04 — CORE

Question: What is your technical confidence level: non-technical, confident user, or developer?

Why: There is no correct level. It tells the AI how to explain choices without assuming terminology or command-line experience.

Effect / if deferred: Explanation style and setup complexity. Continue unrelated useful work.

### CORE-05 — CORE

Question: Where do you work: Codex, Claude Code, ChatGPT or Claude in a browser, or several environments?

Why: Different applications store instructions, skills, and reminders differently. If you do not know the product name, describe where and how you open the AI.

Effect / if deferred: Exact instruction and reminder placement. Continue unrelated useful work.

### GOAL-01 — GOAL

Question: What would a good result look like after 30 days of using AI?

Why: Describe an observable change, such as reducing report preparation from two days to one, rather than “be more efficient.”

Effect / if deferred: None. Continue unrelated useful work.

### GOAL-02 — GOAL

Question: Which matters most: speed, quality, time saved, lower risk, learning, or scale? Please rank them.

Why: These goals can conflict. The ranking helps the AI choose tradeoffs.

Effect / if deferred: None. Continue unrelated useful work.

### GOAL-03 — GOAL

Question: Which mistakes would be inconvenient, and which could cost money, trust, health, rights, or reputation?

Why: This distinguishes tasks needing a quick check from those needing stronger evidence and human approval.

Effect / if deferred: None. Continue unrelated useful work.

### GOAL-04 — GOAL

Question: Are there tasks the AI must never perform?

Why: These are standing prohibitions that urgency or convenience cannot override, such as sending messages in your name or making medical decisions.

Effect / if deferred: None. Continue unrelated useful work.

### GOAL-05 — GOAL

Question: How should value be measured: hours saved, completed outcomes, quality, revenue, fewer errors, or something else?

Why: A simple observable measure helps determine whether the setup actually works and can be revised later.

Effect / if deferred: None. Continue unrelated useful work.

### COMMS-01 — COMMS

Question: Should answers lead with the conclusion or with explanation and context?

Why: A useful default is “conclusion first, details below,” but the person chooses.

Effect / if deferred: None. Continue unrelated useful work.

### COMMS-02 — COMMS

Question: How detailed should answers be by default?

Why: Options may be very brief, moderately detailed, or step-by-step. Complex or risky topics still require essential limitations.

Effect / if deferred: None. Continue unrelated useful work.

### COMMS-03 — COMMS

Question: Should technical decisions be explained through user impact, risk, cost, timing, or implementation detail?

Why: This sets the explanation language rather than testing technical knowledge.

Effect / if deferred: None. Continue unrelated useful work.

### COMMS-04 — COMMS

Question: When should the AI ask, and when may it choose a safe reversible option?

Why: Reversible means easy to undo without data loss or external consequences. This defines the autonomy boundary.

Effect / if deferred: None. Continue unrelated useful work.

### COMMS-05 — COMMS

Question: Do you want facts, interpretations, hypotheses, recommendations, and your decisions shown separately?

Why: These are different evidence states. The distinction is especially useful in research and high-impact projects.

Effect / if deferred: None. Continue unrelated useful work.

### COMMS-06 — COMMS

Question: How should the AI deliver unwelcome conclusions or objections?

Why: Options include direct and brief, gentle with explanation, or consequences first. Important risk must not be hidden for comfort.

Effect / if deferred: None. Continue unrelated useful work.

### AUTH-01 — AUTH

Question: May the AI perform read-only checks without asking each time?

Why: Read-only means viewing and analyzing without changing or sending anything. Define which folders, sites, or work systems this covers.

Effect / if deferred: Unapproved data sources. Continue unrelated useful work.

### AUTH-02 — AUTH

Question: May the AI create and edit local files inside a selected folder?

Why: Limit permission to a precise folder so neighboring data remains untouched.

Effect / if deferred: Local writes. Continue unrelated useful work.

### AUTH-03 — AUTH

Question: Which external actions always require separate approval?

Why: External actions include sending, submitting, publishing, purchasing, or changing an account. List actions the AI must never infer.

Effect / if deferred: All unapproved external actions. Continue unrelated useful work.

### AUTH-04 — AUTH

Question: May messages, forms, publications, or reactions be sent after a preview?

Why: A preview shows the exact content, recipient, and action. Even a general yes may still require approval for each concrete action.

Effect / if deferred: Communications and publication. Continue unrelated useful work.

### AUTH-05 — AUTH

Question: After review, may the AI propose installing skills, plugins, connectors, MCPs, or dependencies?

Why: A yes permits a proposal only, not automatic installation. These components may read files, use the network, or act.

Effect / if deferred: Installation and connection. Continue unrelated useful work.

### AUTH-06 — AUTH
