### Propose one home and a useful next step

Use the existing accepted layout and its actual equivalent paths:

| What the material is for | Proposed location or treatment |
|---|---|
| Incoming material for a known project | That project's inbox; keep the original as a source, not automatically accepted knowledge |
| A standalone task or material not yet assigned | Root inbox if the optional root inbox/work/outputs module is adopted; otherwise leave the source in place and show the proposal |
| A summary, analysis, possible next actions or other working draft | The project's work folder, or work/<task> for a standalone task; link the original |
| A result the person has accepted as ready for use/handoff | The corresponding outputs folder; do not infer readiness from a polished filename or appearance |
| A reviewed explanation useful across projects | Propose exact text for knowledge-base/shared with sources and caveats; routing acceptance alone does not confirm its claims |
| A selected reusable original reference | Propose knowledge-base/sources only when useful, or link its already authoritative home; no second automatic archive |
| Data with a separate processing lifecycle | The project's conditional datasets area, distinguishing originals, intermediate and final data; a CSV alone does not require this module |
| Material explicitly chosen for archiving | The project's conditional archive; age alone is insufficient and archive never means deletion |
| Code or independently maintained product-design sources | Link the existing repository or design source; no Git action, relocation or export is inferred. Ordinary visual drafts/results use project work/outputs |
| A possible personal fact, goal or durable decision | A separate source-bound proposal for the appropriate existing context/decision file; do not silently edit it during sorting |

Preserve the accepted structure: no new profile wrapper, default root datasets/archive or extra project sources hierarchy. Known-project material does not also need a root copy. If all work belongs to projects, the root inbox/work/outputs trio can stay absent. Offer that trio together only when standalone/unassigned work makes it useful, without creating it from a proposal. Existing equivalent locations win. If a standalone task grows into a project, review the exact placement change before acting.

Keep one authoritative original. When several projects need an item, propose references to that original, not competing canonical copies. A reviewed original may remain in its agreed inbox with a clear processing status; emptying the inbox is not the goal. Useful results can be a short summary, a proposed task list or a better reference without any move. A discovered possible action is not executed or scheduled merely because it appears in a note.

Intake can remain entirely in chat. If the person wants to save a new link or note, preview one small reference/note file in the selected inbox with the original link or permitted text, available provenance and reason for keeping it. A link does not authorize downloading a site. Reference an existing file in place unless an exact copy or move is included in the approved proposal; a selected copy must not silently replace the canonical original.
