## Different hosts and input modes

Use the same continuation rules for ChatGPT, Codex and Claude, based on the actual current surface and mode. These names are not capability guarantees. A browser conversation, desktop app, workspace agent and CLI may have different current access. Other assistants follow the generic contract until separately verified.

| Actual available mode | Allowed continuation |
|---|---|
| Existing chat with usable context | Reuse it, even if the old file save failed; do not claim that another chat knows it |
| New chat with a pasted card | Reuse the card's attributable facts within current scope; obtain missing phase instructions if needed |
| Selected readable file or attachment | Inspect the actual content and identity; a path/filename/attachment icon alone is not proof of readable bytes |
| Permitted public link reading | Fetch only exact required method bodies; normal HTML/raw/text variants share the edition identity and read budget |
| No link reading | Copied core works as entry; request the exact short needed body once in ordinary language; no installation/upgrade required |
| Full compatible method already supplied | Use actual relevant instructions without modular refetch; full input is not evidence that personal progress was saved |
| No persistent storage | Work in chat and provide a clearly unsaved copyable card; no automatic future-memory promise |
| Workspace access changed or unavailable | Use the visible safe context/manual route; do not broaden access or recreate absent folders automatically |

Only public method identifiers may appear in method URLs. Never upload the continuation card to resolve a route, add personal state to URL parameters or ask the website to recover a private task. Source access policies remain in force; a mirror is not a way around an access denial.

Read ceilings apply to the current bounded loading episode, not the number of future returns. A fresh host missing actual text may need a fresh bounded load, with known previous failure/context retained. An exhausted episode does not automatically restart after “continue”; changed access or an explicit retry request is handled within current permission and the core read limits. An intermediate unpublished edition need not be fetched: use a supported cumulative change description and coherent available target instructions. When more than one required body is missing, give one clear request for the actual missing set, keeping each block short and avoiding repeated confirmation ceremonies.

## Plain-language examples (English source)

- Known pending detail: “We were reviewing where to keep the two notes. The first destination is agreed; only the second remains.” Then ask that one remaining question.
- No prior context: “I don't have the earlier conversation here. Tell me what you want to continue, or paste the short progress note if you have it.” Do not require both.
- Save failed but context remains: “We can continue from the answers in this chat. The progress note hasn't been saved to the file.”
- Unknown operation outcome: “The connection stopped before I could confirm whether the file was moved. I'll first check the selected source and destination if that access is available.” If unavailable, give one concrete manual verification step; never imply the check occurred.
- Several tasks: “Do you want to continue the notes review or the profile setup?” Use actual known choices.
- Complete recovery input: “I have the instructions. Let's continue with the remaining step.” Continue immediately; no extra English recovery command.

These are templates to adapt to actual evidence and the person's language. They must not introduce a completed action, prior consent or saved state that was not established.
